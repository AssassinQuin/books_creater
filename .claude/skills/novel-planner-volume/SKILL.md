# 卷级大纲设计

> 根据 novel-planner 确定的"每卷做什么"，设计"每章发生什么"。**把握脉络，不追求细节**。世界元素注册、感官5要素、微事件多样性等留给正文写作阶段(novel-chapter-writer)。

## 强制流程

```
Step 0: 增量检测 → 加载框架+数据采集
  ↓
Step 1: Agent — 事件架构师 → 因果链+人物弧光+悬念锚点
  ↓  🔒检查点A: 确认事件架构
Step 2: Agent — 章节设计师 → 逐章大纲+伏笔节奏+声音适配
  ↓
Step 3: 卷级验证 → 三视角审查(读者/作者/人物)
  ↓  🔒检查点B: 确认验证通过(P0必须修复)
Step 4: 保存(DB+文件+审计报告) → git commit
```

## 编排器职责

只负责：**增量检测 + MCP调用 + Agent启动 + 检查点确认 + 保存**。不直接设计事件。

## Step 0: 增量检测与数据采集

### 0.1 增量检测（核心优化）

```python
# 检查是否存在上次的审计报告
audit_report = "novels/{小说名}/审阅报告/V{N}-卷级审计.md"

if audit_report exists:
    # 计算自上次审计以来的变更量
    git_diff = git diff --stat <last_audit_commit> -- "novels/{小说名}/设定/大纲/V{N}-*.md"
    changed_ratio = changed_lines / total_lines

    if changed_ratio < 0.3:
        mode = "增量审计"
        # 只审查变更的章节 + 前后各1章（因果链影响）
        scope = "变更章节及其邻章"
    else:
        mode = "全量审计"
        scope = "全部章节"
else:
    mode = "全量审计"
    scope = "全部章节"

# 展示给用户
print(f"审计模式: {mode} | 范围: {scope}")
```

**增量审计规则**：
- 变更<30%：只审变更章+邻章，复用上次未变更部分的审查结果
- 变更≥30% 或新增卷：全量审计
- 上次审计报告不存在：全量审计
- **强制全量触发**：用户明确要求、卷目标/核心设定变更、新增/删除整章

## Step 1: Agent — 事件架构师

**Agent指令**: `agents/event-architect.md`

### 编排器操作
1. 收集以下数据，打包传给 Agent：
   - 本卷大纲（`设定/大纲/V{N}-{卷名}.md`）
   - 全书骨架（`设定/全书大纲.md` 本卷部分）
   - 活跃角色列表 + 关键角色蒸馏卡（character_list + character_detail）
   - 未回收伏笔列表（foreshadow_list, status='planted'）
   - 上卷末角色状态（从上一卷大纲"人物弧光"表提取）
   - 卷定位（起/承/转/合）+ 全书第几卷
2. 启动 Agent（subagent_type: "general-purpose"），传入数据 + `agents/event-architect.md`
3. Agent 输出事件架构（因果链+起承转合+人物弧光+悬念锚点+伏笔操作）

### Agent 核心方法论
从"卷末谁变了、变到什么状态"反推事件。不要从开头想。
```
卷末状态 - 卷初状态 = 需要发生的变化
每个变化 → 触发事件 → 因果链
```

### Agent 硬约束
- 每章至少3个可辨识事件
- 费笔配额 ≥ 总章数×1.0（费笔定义见 agent 文件）
- 每个主要角色在卷内至少与2个不同角色有独立互动
- 禁止任何角色连续3章无独立出场
- 因果链每个关键事件有显式前因
- 巧合计≤1次/卷且必须有伏笔支撑

## 🔒检查点A: 确认事件架构

编排器展示：

```
【V{N}《{卷名}》事件架构】

情感曲线: {起点} → {转折} → {终点}

起承转合:
  起(Ch?): {概要}
  承(Ch?): {概要}
  转(Ch?): {概要}
  合(Ch?): {概要} → 下卷钩子: {类型}

因果链: {事件1} → {事件2} → ... → {终点}

人物弧光:
  {角色A}: {起点状态} → {触发事件} → {终点状态}
  {角色B}: 不变（理由：{ }）

悬念: 回答了[?] / 新提出[?]

确认后进入章节设计。输入"OK"或修改意见。
```

## Step 2: Agent — 章节设计师

**Agent指令**: `agents/chapter-designer.md`

### 编排器操作
1. 将 Step 1 确认后的事件架构 + 角色蒸馏卡 + 世界观索引打包传给 Agent
2. 启动 Agent（subagent_type: "general-purpose"），传入数据 + `agents/chapter-designer.md`
3. Agent 输出逐章大纲（每章场景序列+伏笔场景化+人物互动矩阵+声音适配）

### Agent 核心方法论
每章是微型故事：开场钩子→主体事件（2-4场景）→章末钩子。
每章至少：1个推进主线的场景 + 1个人物互动场景 + 1个费笔/世界呼吸。

### Agent 硬约束
- 起段/合段每章3-5场景，承段4-6场景，转段5-7场景
- 相邻章场景结构不同（入场/主体/收尾类型轮换，防AI指纹F3）
- 每个伏笔操作有具体场景+执行方式（禁止"在Ch{N}提到"）
- 每章至少2组独立人物互动
- 每卷至少1个"罕见组合"互动（如沈念↔老陈、方岩↔汐）
- 配角有独立于主角的场景——他们有自己的生活
- 声音层标注到场景级
- 新埋伏笔每章≤1个，每卷未回收伏笔≤12个

### 增量模式
如果增量检测发现只改了部分：
- 只重新设计变更影响的主线/支线段落
- 标注受影响的邻卷接口
- 未变更部分保持原样

## Step 3: 卷级验证（三视角审查）

### 增量 vs 全量

| 模式 | 范围 | 三视角 | 交叉检查 |
|------|------|--------|---------|
| 增量 | 变更章+邻章 | 只审变更部分 | 只检查变更部分与未变更部分的接口 |
| 全量 | 全卷 | 三个视角完整审查 | 完整交叉检查 |

### 三视角审查（3个Agent并行）

- **读者视角**: 追读体验（钩子/悬念/爽点间隔/信息投放/情感共鸣）
- **作者视角**: 结构工艺（起承转合/因果链/伏笔管理/节奏控制）
- **人物视角**: 角色一致性（行为符合性格/动机充分/选择必然/OOC检测）

**核心原则**：人物 > 读者 > 作者

### 问题分级
- **P0**: 三视角冲突 / 角色OOC / 因果链断裂
- **P1**: 单视角严重问题
- **P2**: 微调建议

### 🔒检查点B: 确认验证通过

P0→必须修复（回到对应Step）。无P0→进入保存。

## Step 4: 保存

### 文件落盘
```
novels/{小说名}/设定/大纲/V{N}-{卷名}.md          # 卷级故事大纲
```

大纲风格：**像写故事一样写大纲**。读大纲的人应该能"看到"这卷小说的画面——谁在做什么、为什么做、做完了怎样。不用表格堆砌，不写叙事动作注释（留给正文碎片）。

#### 卷级大纲模板

> 把握卷级故事脉络，主线支线交织推进，事件因果清晰可追溯。

```markdown
# V{N}：{卷名}

> **核心情绪**：{一句话概括本卷情感基调}
> **POV锚点**：{主要视角角色}
> **时间跨度**：{本卷大致时间范围}

## 卷级因果链

因为{V{N-1}末状态/初始前提} → 所以{本卷起点事件} → 逼出{核心选择} → 雪球{连锁反应} → 到{卷末状态}
没变的是{遗憾/保留的困境}。

## 故事脉络

> 主线与支线交织推进，按小说行文节奏展开。每段写清：谁在做什么→为什么→结果怎样→怎么引出下一段。支线在自然交汇处出现，不单独罗列。

### 起

{故事开篇建立。300-500字。}

写清：场景是什么样、主角在干什么、他的日常是什么样的、这个世界怎么运转。
支线在此阶段的苗头：{哪些支线在起段埋下第一颗种子——通过什么事件/细节暗示}
事件清单（起段涉及的具体事件）：
- {事件1}：{谁做了什么→结果→引出什么}
- {事件2}：...
费笔清单（起段至少{段章数}个）：
- {费笔1}：{谁+什么日常/细节/世界呼吸}（融入{哪个主线场景}/独立场景）
读者此刻的感受：{从什么状态到什么状态}

### 承

{事件推进，冲突升级。400-700字。}

写清：主要矛盾怎么升级、哪些势力/角色开始行动、支线怎么和主线交织。
支线在此阶段的推进：{每条支线在承段做了什么——不是单独描述，是在主线事件中自然出现}
事件清单（承段涉及的具体事件）：
- {事件1}：{因果链——因为前段的X，所以发生了这个}
- {事件2}：...
- {支线交汇点}：{哪条支线在这个事件中与主线交汇，结果是什么}
费笔清单（承段至少{段章数÷2向上取整}个）：
- {费笔1}：{谁+什么日常/细节/世界呼吸}（融入{哪个主线场景}/独立场景）
读者此刻的感受：{紧张/不安/期待...}

### 转

{转折/高潮，核心事件爆发。400-700字。}

写清：什么真相被揭露/什么关系断裂或重建/角色被逼到什么选择面前。
这是全卷情感密度最高的段落——写清角色的反应和选择，不只写"发生了什么"。
支线在此阶段的爆发：{哪些支线在转折点达到卷内高潮或收束}
事件清单（转段涉及的具体事件）：
- {事件1}：{这是全卷核心事件，写清因果链和角色反应}
- {事件2}：...
关键对话/核心句（如有）：
> "{角色}"："{全文需保留的核心对话，不超过3句}"
费笔清单（转段至少{段章数÷2向上取整}个）：
- {费笔1}：{谁+什么日常/细节/世界呼吸}（融入{哪个主线场景}/独立场景）
读者此刻的感受：{从什么状态被击穿到什么状态}

### 合

{收尾+下卷钩子。200-400字。}

写清：卷末的新平衡是什么、角色到了什么状态、留了什么悬念引向下卷。
支线在此阶段的状态：{每条支线在卷末停在什么位置——收束了还是悬着}
事件清单（合段涉及的具体事件）：
- {事件1}：{收束或铺垫}
- {事件2}：...
费笔清单（合段至少{段章数}个）：
- {费笔1}：{谁+什么日常/细节/世界呼吸}（融入{哪个主线场景}/独立场景）
下卷钩子：{什么悬念/事件/细节指向V{N+1}}
```

**模板核心要求**：
- **故事脉络是主体**，占全卷大纲70%以上篇幅。读大纲 = 读故事梗概，不是读清单
- **主线支线交织写**，不分开罗列。支线在"起/承/转/合"中自然出现，交汇点明确标注
- **事件清单是骨架**，每段列出具体事件（谁做了什么→结果→引出什么），让读者看到因果链
- **费笔清单**，每段列出费笔事件/细节（≥段章数×1），融入主线场景或独立场景均可，但不能没有
- **关键对话不超过3句**，只留全书级核心句。其他对话留给正文碎片
- **篇幅参考**：起300-500字 / 承400-700字 / 转400-700字 / 合200-400字。全卷故事脉络1500-2500字

**硬指标（不达标拒绝存盘）**：
- 事件密度：每章≥3个可辨识事件，每段事件清单数量≥段章数×3
- 费笔配额：全卷≥总章数×1.0个费笔事件/细节
- 人物互动：每个主要角色与≥2个不同角色有独立互动场景，罕见组合≥1个/卷
- 伏笔场景化：每个伏笔操作有具体场景+执行方式，禁止"在Ch{N}提到/暗示"
- 配角独立场景：每个配角（老陈级及以上）至少1个独立于主角的场景

## 与上下层的关系

- **上层：novel-planner**：提供"每卷做什么"（卷目标/核心事件类型/钩子设计）
- **本层：novel-planner-volume**：设计"每章发生什么"——**把握脉络，不注册细节**
- **下层：novel-chapter-writer**：根据本层大纲生成正文。**世界元素注册在正文写作阶段完成**（Ch9-2老猎人事件后才会出现"源质分级名单"这种具体元素，卷级大纲无法预知具体描写）

## 本层不做的事（明确边界）

| 不做 | 原因 | 谁做 |
|------|------|------|
| 世界元素注册（具体感官/功能/外观） | 卷级只知道事件框架，具体物品/地点/能力的五感细节是正文写作时才确定的 | novel-chapter-writer (Agent 2 Creative Director) |
| 感官5要素分配 | 每个场景的视觉/听觉/嗅觉在正文写作时才有意义 | novel-chapter-writer (Agent 3 Engine Coordinator) |
| 逐章字数精确控制 | 大纲阶段预估章节字数，实际字数由 writing-constraints.md 在写作时控制 | novel-chapter-writer + validate_chapter |
| 完整对话撰写 | 大纲只留全书级核心句（≤3句），其余对话留给正文 | novel-chapter-writer (Agent 4 Text Generator) |

**本层新增职责**（V2优化后）：
| 新增职责 | 原因 |
|---------|------|
| 费笔配额设计 | 费笔事件需要在因果链中有位置，不能正文时临时塞。大纲阶段规划"谁在哪里做了什么日常" |
| 人物互动矩阵 | 确保角色出场均衡、罕见组合不遗漏——这是结构问题不是正文细节 |
| 伏笔场景化 | 每个伏笔必须有具体埋设场景设计——"在Ch{N}提到"不是大纲，是偷懒 |
| 配角独立场景 | 确保配角有自己的生活线——大纲不规划，正文就会把所有配角写成围着主角转 |

## 增量审计设计

### 为什么需要增量
百万字小说14卷，每卷15-20章。每次改几章就全量审计 = 浪费context和时间。

### 增量检测依据
- `git diff --stat` 计算变更比例
- 变更<30% → 增量（只审变更章+邻章）
- 变更≥30% → 全量
- 审计报告持久化在 `审阅报告/` 目录

### 审计报告的作用
- **断点续传**：下次审计时读取上次结果，未变更部分直接复用
- **变更追溯**：`修改记录` 表记录每次变更
- **问题追踪**：P0/P1问题的修复状态持续跟踪
