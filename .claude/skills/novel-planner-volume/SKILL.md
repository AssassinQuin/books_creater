# 卷级大纲设计

> 根据 novel-planner 确定的"每卷做什么"，设计"每章发生什么"。**把握脉络，不追求细节**。世界元素注册、感官5要素、微事件多样性等留给正文写作阶段(novel-chapter-writer)。

## 强制流程

### 全量模式（首次/大改）

```
Step 0: 增量检测 → 加载框架+数据采集
  ↓
Step 1: Agent — 事件架构师 → 因果链+人物弧光+悬念锚点
  ↓  🔒检查点A: 确认事件架构
Step 2: Agent — 章节设计师 → 逐章大纲+伏笔节奏+声音适配
  ↓
Step 3: 卷级验证 → 三视角审查(读者/作者/人物)
  ↓  🔒检查点B: 确认验证通过(P0必须修复)
Step 4: 保存(DB+文件+审计报告) → git commit
```

### 增量扩展模式（用户修改/扩展特定章节）

当用户对已生成大纲提出**局部修改**（如"Ch001加一个异灵追击场景""Ch003时间线不对"）时，**不重跑全流程**，走以下捷径：

```
Step 0: 定位影响范围
  ↓  读取现有逐章大纲，确定用户要改的章节
  ↓  检查因果链影响：改动是否波及邻章？
Step 1: 只修改目标章节
  ↓  编排器直接修改指定章节的场景/事件
  ↓  如需新增伏笔/角色，编排器调MCP创建
Step 2: 邻章校验
  ↓  检查修改后的章节与前后章的因果链/时间线是否连贯
  ↓  如有断裂，扩展修复范围
Step 3: 保存 → git commit
```

**触发条件**：用户说"改Ch{N}""扩展Ch{N}""Ch{N}加个场景"等局部修改指令。
**不触发**：用户说"重新生成""重做大纲"→走全量模式。

## 编排器职责

只负责：**增量检测 + MCP调用 + Agent启动 + 检查点确认 + 保存**。不直接设计事件。

## Step 0: 增量检测与数据采集

### 0.1 增量检测（核心优化）

```python
# 检查是否存在上次的审计报告
audit_report = "novels/{小说名}/审阅报告/V{N}-卷级审计.md"

if audit_report exists:
    # 计算自上次审计以来的变更量
    git_diff = git diff --stat <last_audit_commit> -- "novels/{小说名}/设定/大纲/V{N}-*.md"
    changed_ratio = changed_lines / total_lines

    if changed_ratio < 0.3:
        mode = "增量审计"
        # 只审查变更的章节 + 前后各1章（因果链影响）
        scope = "变更章节及其邻章"
    else:
        mode = "全量审计"
        scope = "全部章节"
else:
    mode = "全量审计"
    scope = "全部章节"

# 展示给用户
print(f"审计模式: {mode} | 范围: {scope}")
```

**增量审计规则**：
- 变更<30%：只审变更章+邻章，复用上次未变更部分的审查结果
- 变更≥30% 或新增卷：全量审计
- 上次审计报告不存在：全量审计
- **强制全量触发**：用户明确要求、卷目标/核心设定变更、新增/删除整章

## Step 1: Agent — 事件架构师

**Agent指令**: `agents/event-architect.md`
**加载引擎**:
- `skill_loader("novel-planner-volume", "engine", "causality")` — 因果逻辑网四步法（世界观刑具化→因果链编织→雪球效应→不可逆节点）
- `skill_loader("novel-planner-volume", "engine", "relationship")` — 人物关系变化追踪（互动矩阵设计时参考）

### 编排器操作
1. 收集以下数据，打包传给 Agent：
   - 本卷大纲（`设定/大纲/V{N}-{卷名}.md`）
   - 全书骨架（`设定/全书大纲.md` 本卷部分）
   - 活跃角色列表 + 关键角色蒸馏卡（character_list + character_detail）
   - 未回收伏笔列表（foreshadow_list, status='planted'）
   - 上卷末角色状态（从上一卷大纲"人物弧光"表提取）
   - 卷定位（起/承/转/合）+ 全书第几卷
   - 因果逻辑引擎（`engines/causality.md`）— Agent 参考其中的四步构建法和因果链公式
   - 关系追踪引擎（`engines/relationship.md`）— Agent 参考关系强度量表和变化追踪
2. 启动 Agent（subagent_type: "general-purpose"），传入数据 + `agents/event-architect.md`
3. Agent 输出事件架构（因果链+起承转合+人物弧光+悬念锚点+伏笔操作）

### Agent 核心方法论
参考 `engines/causality.md` 的因果逻辑网构建法，结合自主方法论：

**自主方法论**：从"卷末谁变了、变到什么状态"反推事件。不要从开头想。
```
卷末状态 - 卷初状态 = 需要发生的变化
每个变化 → 触发事件 → 因果链
```

**因果逻辑网补充**（从 causality.md 集成）：
```
事件N = f(事件N-1的 consequences, 角色 choices, 世界观 rules)
不是"第N天主角去了X地方"——而是"因为事件N-1导致Z后果，主角被迫做出A选择"
四步法：世界观刑具化→因果链编织→雪球效应→不可逆节点
```

Agent 输出的事件因果链必须通过"可替换性测试"和"可删减性测试"（来自 causality.md 的验证标准）。

### Agent 硬约束
- 每章至少3个可辨识事件
- 费笔配额 ≥ 总章数×1.0（费笔定义见 agent 文件）
- 每个主要角色在卷内至少与2个不同角色有独立互动
- 禁止任何角色连续3章无独立出场
- 因果链每个关键事件有显式前因
- 巧合计≤1次/卷且必须有伏笔支撑

### POV时间线铁律（强制）

1. **主角时间线优先**：所有事件以主角（本卷POV锚点角色）的时间线为锚点。主角在D1上午做什么→D1下午做什么→D2做什么，时间线不可跳跃。
2. **其他角色POV = "主角不知道的时候"**：非主角视角场景必须标注"此时主角在做什么"。其他角色的行动是主角时间线的**暗面**——主角不知道，但读者知道。
3. **禁止跳过主角**：不能出现"主角3天没出场，其他角色在推进剧情"的情况。主角必须持续在场，即使他在做日常琐事。
4. **时间线锚点标注**：每个场景必须标注时间点（D1上午/D2傍晚等），且与主角时间线对齐。

### 内容密度规则（强制）

1. **事件→字数映射**：每个可辨识事件至少支撑800-1000字正文展开（含动作链+对话+环境+内心）。
2. **每章事件数下限**：≥4个主线事件（4事件×800字=3200字，保证3000+字底线）。
3. **微事件体系**：每章3-5个微事件（每个支撑200-400字），是章节内容的**血肉层**。微事件不是主线事件，而是穿插在主线场景中的小动作/小细节/小变化：

| 微事件类型 | 定义 | 示例 |
|-----------|------|------|
| 日常仪式 | 角色的固定行为模式 | 沈野三堆分法、沈念呼气攥拳吸气松开 |
| 角色特点变化 | 微小的行为/态度偏移 | 沈野多放一块碎渣到中等堆、沈念笑的时间短了半秒 |
| 角色成长信号 | 能力/认知的微小进步 | 沈野手感更准了、沈念注意到韩朗的额外操作 |
| 支线伏笔 | 非主线伏笔的微小推进 | 方岩多看沈念一眼、鸦在窗外停了一下 |
| 因果微链 | 小事件的因果连接 | 因为昨天下雨→今天管道积水→拾荒路线改变 |
| 世界呼吸真实感 | 世界在角色之外运转的证据 | 公告栏新贴了一张纸、隔壁管道有人搬走了、老陈换了新铁板 |
| 配角专场 | 配角独立于主角的微小生活 | 老陈擦铁板时哼歌、韩朗下班后去换物摊买干菜 |

4. **世界观展开配额**：每章至少1个场景通过事件/互动自然展开世界观（不是堆设定旁白，是通过角色行动展示世界运转方式）。
5. **主角戏份保底**：主角在场场景≥全章场景数的60%。主角不能连续2章无独立事件。
6. **伏笔因果逻辑**：每个伏笔必须有"为什么在这里埋"的因果理由——不是"剧情需要"，而是"这个角色在这个场景中自然会注意到/接触到这个信息"。

### 伏笔自然设计规则（强制——冰山理论）

**核心原则**：伏笔不是"告诉读者这里有个线索"，而是"让事件自然发生，读者事后回看才发现早有铺垫"。

**设计方法**：先果后因
1. **当前章节**：事件自然发生，读者看到的是"果"——角色做了一个选择/遇到了一个情况/注意到了一个细节。这个事件本身有充分的表面动机，不需要"伏笔"来解释。
2. **后续章节**：揭示"因"——读者回看才发现，那个看似自然的事件背后有更深层的原因。

**示例**：
```
❌ 硬塞伏笔：
Ch001: 沈野捡到一块奇怪的残片，"他感到这块残片有些不同寻常"——
读者反应：作者在告诉我这很重要，记下来。

✅ 自然伏笔：
Ch001: 沈野拾荒时摸到一块纹路复杂的残片，揣着没扔——因为碎渣成色好，能多换半碗面。
读者反应：他只是在拾荒，很正常。
Ch004: 沈野发现残片的纹路和管壁上的不一样——他以前没注意过，因为以前没在这么深的位置拾荒过。
读者反应：嗯，拾荒的细节，有意思。
Ch018: 沈野在荒原第一夜转了转残片，手感告诉他——这不是碎渣。
读者回看Ch001：原来他一开始就"摸"到了不同，只是当时以为是碎渣。
```

**伏笔设计三禁止**：
1. **禁止"他感到不同寻常"**——角色不会知道这是伏笔，他只会在做自己的事
2. **禁止"这块残片似乎隐藏着秘密"**——这是作者在说话，不是角色在行动
3. **禁止"为伏笔而伏笔"**——每个伏笔事件必须有独立的表面动机（拾荒换面/递水因为渴/看公告栏因为无聊），伏笔是附加层，不是主层

## Step 2: Agent — 章节设计师

**Agent指令**: `agents/chapter-designer.md`
**加载引擎**:
- `skill_loader("novel-planner-volume", "engine", "scene-type")` — 6种场景类型写作策略（对话/动作/氛围/心理/日常/混合，影响每章场景结构选择）

- `skill_loader("novel-planner-volume", "engine", "author-voice")` — 作者声音三层架构（影响场景的声音层标注）

### 编排器操作
1. 将 Step 1 确认后的事件架构 + 角色蒸馏卡 + 世界观索引打包传给 Agent
2. 将场景引擎（`engines/scene-type.md`, `engines/scene-composition.md`）和作者声音引擎（`engines/author-voice.md` + 对应变体）作为附加参考传入
3. 启动 Agent（subagent_type: "general-purpose"），传入数据 + `agents/chapter-designer.md`
4. Agent 输出逐章大纲（每章场景序列+场景类型标注+伏笔场景化+人物互动矩阵+声音适配+场面密度分配）

### Agent 核心方法论
每章是微型故事：开场钩子→主体事件（2-4场景）→章末钩子。
每章至少：1个推进主线的场景 + 1个人物互动场景 + 1个费笔/世界呼吸。

### Agent 硬约束
- 起段/合段每章3-5场景，承段4-6场景，转段5-7场景
- 相邻章场景结构不同（入场/主体/收尾类型轮换，防AI指纹F3）
- 每个伏笔操作有具体场景+执行方式（禁止"在Ch{N}提到"）
- 每章至少2组独立人物互动
- 每卷至少1个"罕见组合"互动（如沈念↔老陈、方岩↔汐）
- 配角有独立于主角的场景——他们有自己的生活
- 声音层标注到场景级
- 新埋伏笔每章≤1个，每卷未回收伏笔≤12个

### POV时间线铁律（同Step 1，章节设计师必须遵守）

1. **主角时间线锚定**：每章场景必须按主角时间线排列。场景序列 = 主角的一天/几天。
2. **非主角场景 = 暗面**：沈念独场、方岩独场等，必须标注"此时沈野在做什么"。读者看到的是"主角不知道的暗面"。
3. **时间线连续性**：相邻章的时间线必须连续或可推算。不能Ch001是D1，Ch003跳到D5，中间D2-D4主角在做什么？
4. **场景时间标注**：每个场景必须写明"D{N}{时段}"，时段可选：凌晨/上午/中午/下午/傍晚/夜晚。

### 内容密度规则（同Step 1，章节设计师必须遵守）

1. **每章≥4个可辨识主线事件**（每个事件支撑800-1000字正文）。
2. **每章3-5个微事件**（每个支撑200-400字），穿插在主线场景中。微事件类型：日常仪式、角色特点变化、角色成长信号、支线伏笔、因果微链、世界呼吸真实感、配角专场。
3. **世界观展开**：每章至少1个场景通过角色行动展开世界观。方式：拾荒流程展示碎渣经济、灵站排队展示制度、市集换物展示物价、修灯展示壁盾遗产。**禁止设定旁白**。
4. **主角戏份保底**：主角在场场景≥60%。主角缺席的场景必须有叙事功能（揭示主角不知道的信息）。
5. **伏笔因果**：每个伏笔操作必须回答"为什么是这个角色在这个场景接触到这个信息"。

### 增量模式
如果增量检测发现只改了部分：
- 只重新设计变更影响的主线/支线段落
- 标注受影响的邻卷接口
- 未变更部分保持原样

## 增量审计设计

### 为什么需要增量
百万字小说14卷，每卷15-20章。每次改几章就全量审计 = 浪费context和时间。

### 增量检测依据
- `git diff --stat` 计算变更比例
- 变更<30% → 增量（只审变更章+邻章）
- 变更≥30% → 全量
- 审计报告持久化在 `审阅报告/` 目录

### 审计报告的作用
- **断点续传**：下次审计时读取上次结果，未变更部分直接复用
- **变更追溯**：`修改记录` 表记录每次变更
- **问题追踪**：P0/P1问题的修复状态持续跟踪
