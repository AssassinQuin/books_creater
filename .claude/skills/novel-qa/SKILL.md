# 小说质量保障

<what-to-do>

## 强制流程

```
B3审阅: 加载上下文 → 多Agent并行扫描 → 🔒评分卡 → 汇总报告 → 存盘
C4设定审查: 全量加载 → 6维度审查 → 🔒问题清单 → 修复 → 级联同步
C2诊断: health_check → 指标对比 → 🔒破局方案
C3更新: 改数据 → db_search找影响 → 🔒确认 → 执行 → 验证
```

输出到 `novels/{小说名}/审阅报告/`。无文件输出 = 流程未完成。

## 问题分级标准

分级逻辑：以**读者流失风险**和**修复成本**为双轴判定。风险越高、越晚修复代价越大，级别越高。

| 级别 | 判定标准 | 处理要求 |
|------|---------|---------|
| P0-致命 | 因果链断裂 / 人物OOC / 设定矛盾 / 违禁词 / **术语违规**（使用现代科技术语替代灵能术语） | 必须修复，阻断发布。此类问题会直接摧毁读者信任，无法通过后续章节弥补。 |
| P1-严重 | 伏笔未回收 / 节奏断层 / 质量波动过大 / **新术语缺乏文化出处** | 必须修复，限1轮内。拖延会导致伏笔积压或世界观可信度持续下降。 |
| P2-中等 | 描写冗余 / 对话平淡 / 爽点不足 | 应当修复，可延期至下一轮迭代。影响阅读体验但不阻断理解。 |
| P3-轻微 | 标点不均 / 用词重复 / 格式不统一 | 批量处理，不阻塞当前流程。可在润色阶段统一解决。 |

**为什么这样分级**：P0/P1 的共同点是在读者心中种下"作者不专业"或"设定崩了"的种子，这种印象一旦形成极难逆转；P2/P3 则属于"写得不够好"而非"写错了"，可以渐进优化。

## B3: 大纲审阅（触发：审阅大纲）

加载：`skill_loader("novel-qa", "engine", "outline-review")`

Phase 1: 10维度Agent审计（结构 / 起承转合 / 伏笔密度 / 人物弧光 / 支线检验 / 情绪曲线 / 悬念密度 / 世界观一致性 / 因果链 / 可读性）
- 因果链断裂 → 自动判P0，参考 `skill_loader("novel-qa", "engine", "causality")`

Phase 2: P0/P1修复（每问题3方案 + 代价评估）

Phase 3: 重评
- 通过阈值：综合得分处于前20%~30%区间（优秀档）
- 最多迭代3轮，超过仍未通过则退回重新规划

**为什么设迭代上限**：大纲阶段无限循环会挤压正文写作时间，3轮是"足够修正明显问题"与"避免完美主义陷阱"的平衡点。

## B3: 正文审阅（触发：审阅正文 / 校对）

### Step 1: 加载上下文

- 角色状态（`character_get` + `chapter_get_context`）
- 卷级大纲（`novels/{小说名}/设定/大纲/V{卷号}-{卷名}.md`）
- 全书支线总图（`novels/{小说名}/设定/大纲/支线总图.md`）
- 世界观数据（`world_query(novel_name="这次不一样了")` 优先；返回空时回退读 `设定/世界观.md`）
- 作者声音定义（`engines/author-voice.md`）
- 🔒 术语规范（`lorecraft/SKILL.md` + `lorecraft/references/term-map.md` — 正文审阅必须检查术语合规性）

### Step 2: 多Agent并行扫描

**Agent-人物**：OOC检测 / 知识矛盾 / 说话风格一致性 / 关系合理性

**Agent-逻辑**：时间线连贯 / 经济系统一致 / 伏笔回收状态 / 物品使用逻辑

**Agent-质量**：战斗场面质量 / 章节结构 / 爽点分布 / NPC活跃度 / 写作风格 / AI指纹(F1-F16)

**Agent-术语：术语合规审查**
- 加载 `lorecraft/references/term-map.md`，逐章扫描**术语偏离**（如使用"数据/系统/信号/参数/权限/终端/频率"等现代科技术语替代灵能术语）
- 标记违规位置 + 按映射表给出替换建议
- 检查新术语是否有文化出处
- 检查势力 / 能力 / 地点术语是否与已注册元素一致

**为什么强调"术语偏离"而非"禁止"**：灵能玄幻世界观需要保持术语的文化根脉一致性。现代科技术语会瞬间抽离读者的沉浸感——不是因为这些词本身有错，而是因为它们携带了错误的认知框架（工业化、数字化、去神秘化）。替换原则：用有历史纵深或神秘感的词汇替代。

**Agent-支线：支线完整性审查**
- 本卷支线节点是否按全书总图执行
- 支线-主线交织方式是否清晰
- 支线角色出场是否突兀
- 支线三检验是否通过

**Agent-三视角：3个独立Agent并行审查**
- **Agent-读者**：加载 `engines/reader-perspective-agent.md` → 按**章节级标准**审查（开头钩子 / 信息不跳级 / 悬念管理 / 角色识别 / 场景定位 / 情感共鸣 / 结尾期待 / 逻辑跳跃 / 设定突兀 / 人物行为 / 时间线）
- **Agent-作者**：加载 `engines/author-perspective-agent.md` → 按**章节级标准**审查（起承转合 / 伏笔操作 / 节奏变化 / 主题传达 / 结构力度 / 信息投放 / 场景结构）
- **Agent-人物**：加载 `engines/character-perspective-agent.md` → 按**章节级标准**审查（POV行为符合性格 / 对话符合风格 / 知识边界 / 动机充分 / 情感反应真实 / 选择有代价 / 微表情动作）
- 交叉检查：读者vs作者 / 读者vs人物 / 作者vs人物（由编排器汇总后执行）

### Step 3: 硬约束复核

`validate_chapter(chapter_text)` —— 写时自检的补充，不替代。

### Step 4: Smell Test（借鉴humanize）

核心问题：**这一章读起来像人写的，还是像AI生成的？**

检测方法：让模型以普通网文读者身份判断。若回答"像AI"→标记为P1，要求重写关键段落。

**常见AI写作特征（应转化为更具画面感和人物特异性的表达）**：
- 旁白式心理总结（"他知道/她明白"）→ 应转化为动作、微表情或对话中的潜台词
- 高压场景角色永远从容 → 应让角色有真实的生理反应（颤抖、喘息、失误）
- 连续段落长度高度一致 → 应打破节奏，长短交错
- AI过渡词堆砌（"值得一提的是/不禁/缓缓"）→ 应使用场景化的过渡（一个动作、一个声音、一个视角切换）

**为什么这样做**：AI文本的"干净"恰恰是问题——人类写作有毛边、有犹豫、有信息遗漏。Smell Test不是找错误，而是找"过于正确"的不自然感。

### Step 5: 问题分级 P0/P1/P2/P3

| 级别 | 判定标准 |
|------|---------|
| P0 | 三视角冲突（人物逻辑 vs 作者结构）/ 因果链断裂 / 人物OOC |
| P1 | 单视角严重问题 / 伏笔未回收 / 节奏断层 / Smell Test失败 |
| P2 | 单视角中等问题 / 描写冗余 / 对话平淡 |
| P3 | 轻微问题 / 标点不均 / 用词重复 |

### Step 6: 输出审阅报告

评级标准（按百分位分档）：
- **A（优秀）**：得分处于前20%~25%区间，各维度均衡，无明显短板
- **B（良好）**：得分处于前25%~40%区间，有亮点但存在可修复的局部问题
- **C（合格）**：得分处于中间40%~60%区间，有明显缺陷但不影响主线理解
- **D（不合格）**：得分处于后30%~40%区间，存在P0/P1级问题或整体质量不达标

报告必须包含：三视角审查结果 + Smell Test结论 + 具体修改建议（非笼统评价）。

## C4: 设定审查（触发：审设定）

1. `world_query` + `character_list` + `relation_list` + `foreshadow_list` 全量加载
2. 6维度审查：内部自洽 / 人物一致 / 物品合理 / 历史可信 / 关系完整 / 伏笔可行
3. 🔒问题清单 → 修复方案 → 执行 → 级联同步（受影响的章节 / 人物 / 伏笔）

## C2: 健康诊断（触发：诊断 / 卡文）

`health_check(novel_name="这次不一样了")` → 6指标：伏笔积压率 / 配角活跃gap / 升级节奏 / 日常密度 / 暗线推进 / 卷完成度

→ 低于阈值项 → 破局策略（加事件 / 减日常 / 回收伏笔 / 激活配角）

**阈值设定逻辑**：各指标以"读者流失临界点"为基准，而非绝对数值。例如伏笔积压率超过一定阈值后，读者会丧失追读动力；配角活跃gap过大，读者会忘记该角色存在。

## C3: 级联更新（触发：改设定 / 改人物）

1. 更新数据
2. `db_search(novel_name="这次不一样了", 关键词)` 扫描全部影响范围
3. 🔒确认修改清单（影响章节 / 人物 / 伏笔 / 时间线）
4. 执行修改
5. 验证一致性

**为什么必须全量扫描**：局部修改在长篇小说中几乎不存在——改一个设定往往牵动多条人物线和时间线。db_search 的目的是让修改者看到完整的"涟漪效应"，避免修了一处、崩了另一处。
